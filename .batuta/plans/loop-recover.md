# Plan — loop --recover and --reconcile for parked attempts
<!-- inputs: profile.md@sha256:e18a00765937 routing.md@sha256:bdb31fda5c7d -->

**Goal:** Give the conductor two operations for a parked attempt, so nobody cherry-picks or runs gates by hand (Tempo retrospective 4.2 and 4.3). `batuta loop --recover <delivery> <task>` takes a task parked in `waiting_input`, runs the gates of a normal attempt in its existing worktree, and records a candidate that the delivery then integrates, or leaves the task waiting with the failures recorded. `batuta loop --reconcile <delivery> <task>` prints, read-only, how the task's parked ref merges into the delivery branch, conflicts included.
**Created:** 2026-10-12 · **Status:** approved

## Decisions and context
Scope decided with the maintainer on 2026-10-12, revised twice the same day after `batuta council` returned REVISE (sixteen findings, then twelve; all accepted; `.batuta/councils/2026-10-12-loop-recover/` and `-r2/`). `--recover` covers `waiting_input` only: the worktree, the branch, the parked ref and the ask file survive there and the delivery is still open. A `blocked` delivery is terminal and already bookkept (worktree and branch removed, a `loop blocked` commit on the branch, `--resume` refuses it); recovering it is a later plan, and this plan gives it `--reconcile` only. The verifier runs in a recovery exactly when it would in a normal attempt (`gates.NeedsVerifier`), as a read-only executor session. The claim-evidence judgment does not run in a recovery: it judges what an executor session claimed, the parked session stopped at a question and its output is not in the journal, so the conductor's gates are the evidence. A recovery does not answer the question: the pause is closed and the journal says the conductor recovered the task (`source: conductor` on the gate and candidate records; no new field in the graph JSON). When a gate fails, the task's state does not change and no execution is spent.

Frozen signatures, never changed: `NewArtifactLoader`, `BuildCandidateBindings`, `Selector.Select`, `RecordFailure`, `SettleWave`, and the argument structs they take. Add methods and files; do not change the behaviour of `RecordCandidate`, `RecordAnswer`, `RecordQuestion` or `runAttempt` for existing callers. Tests are table-driven where cases repeat, with `t.Parallel()` and `tempDir(t)`; loop end-to-end tests follow their neighbours in `loop/loop_test.go` (most do not run in parallel). Run Go as `env -u GOROOT go test ...` on this machine; if the sandbox refuses to run Go, finish without running it and say so (the loop's gates run the suite). A proof is one `go test -run <name>` command: give each test exactly the name its criterion uses, never reuse an existing test name, and never edit or weaken an existing test to pass.
