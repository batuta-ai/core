## Decisions and context

Go standard library only, frozen exported signatures outside additions named here, conventional commits, tests against httptest and fake judges only, no secrets in fixtures, journal records or logs. Read `.batuta/judge-research.md` sections 4 and 5 and `docs/judge.md` first. The `judge` package (merged in PR #101) provides `judge.LoadConfig(root, getenv)`, `Config.Judge(getenv)`, `Config.Decision(name)` with `Mode off|shadow|enforce` and `Threshold`, `judge.Traced` with `judge_intent`/`judge_result` record structs, and `judge.StateDigest`.

Safety rules, not negotiable: the judge may only make an attempt stricter. In `enforce` it can turn a passing report into a failure; it never turns a failure into a pass, never clears a gate, never marks a task satisfied. `shadow` records and changes nothing. Any error from the judge, including `ErrUnavailable`, is recorded and ignored. The state is built by code from bounded evidence; executor output is untrusted input to the judge. Every `noul` is gated on its probability with the decision threshold (default 0.9); there is no confidence on `noul`.

**Task 1.** New `loop/judgment.go`. `ClaimEvidenceInput{Task routing.PlanTask; Criteria []gates.Criterion; Report gates.Report; OutputTail string; Progress []executor.ProgressEvent; ChangedPaths []string; TreeChanged bool}` and `BuildClaimEvidenceState(input, maxBytes int) (any, error)`: a JSON object with `task` (id, title, scope), `criteria` (index, text, proof command, proof verdict pass/signal), `executor_report` (the last 60 lines of stdout+stderr, capped at 8 KiB, with `BATUTA-PROGRESS` and `TASK n:` lines kept whole), `progress` events, `tree` (changed or equal to base, changed paths relative to the repository), `verifier` (signal and detail when present), and `outcome` (report.Passed and the failing gate names); when the object exceeds `maxBytes` trim `executor_report` first, then `changed_paths`, and fail only if the skeleton alone exceeds the budget. Redact anything under the workspace root to a repository-relative path and drop lines that look like `KEY=value` with an uppercase key. `ClaimEvidenceQuestions()` returns the two `judge.Question` values with instructions written for a literal reader: `claim_unsupported` = "The executor's report claims work (files changed, tests passed, criteria done) that the tree, proof and verifier evidence in this state does not show." with criteria `{"true": "a claim in executor_report is contradicted by tree, proofs or verifier", "false": "every claim in executor_report is consistent with the evidence"}`; `verifier_contradicted` = "The verifier's DONE lines are contradicted by a failed proof or by the executor's own report." with analogous criteria. Journal kinds `KindJudgeIntent = "judge_intent"` and `KindJudgeResult = "judge_result"` in `loop/runner.go` beside the other kinds; records carry the task id and the `judge` trace structs as detail; the graph is untouched. `loop.Options` gains `Judge judge.Judge` and `JudgeConfig judge.Config`; `cmd/batuta/main.go` `runLoop` loads the config with `judge.LoadConfig(root, os.Getenv)` and builds the judge, and the dry run prints one line `judge     <provider chain or off>`.

**Task 2.** In `runAttempt`, after `report.Decide()` and before the `report.Passed` branch, call `r.judgeClaimEvidence(ctx, ac, report, result, treeChanged, changedPaths)` when `r.judge != nil` and `r.judgeConfig.Decision("claim_evidence").Mode != off`. It records `KindJudgeIntent`, asks through `judge.Traced` with a sink that appends `KindJudgeResult`, and returns a `judgment{Asked bool; Unavailable string; Answers map[string]float64}`. In `shadow` nothing else happens. In `enforce`, when `report.Passed` and either probability is at or above the threshold, set `report.Passed = false`, append a synthetic failing verdict `gates.Verdict{Name: "judge", Pass: false, Signal: "claim_evidence: claim_unsupported 0.93 (threshold 0.90)", Detail: <the executor claims most at odds, quoted from the state>}` to `report.Proofs` so `Failures()` and the trail show it, and route the failure through `recordFailure` with a new `blockerClaimUnsupported = "claim_unsupported"` placed after `blockerVerifier` in `blockerCode`'s priority. Do not consult the judge for attempts that ended in a question, a rate limit, an executor error or a reconciliation block. Extend the existing loop fixtures with a fake `judge.Judge` injected through `Options.Judge`. Document in `docs/loop.md` (one paragraph in the gates section) and in `docs/judge.md` (the `claim_evidence` decision, the state it sees, the two keys, `shadow` versus `enforce`, the threshold, and the rule that enforce only fails attempts).

**Task 3.** `batuta judge replay --journal <path> [--runs <dir>] [--config <path>] [--decision claim_evidence]`. For each `gates_reported` record with a matching `executor_finished` record, locate the run log `<runs>/<date>-<slug>-<task>-e<n>.out.log` (default `<workspace>/.batuta/runs`), rebuild the state with `BuildClaimEvidenceState` from the journal detail and the log, ask the judge and print `task_1 e1 outcome=already_satisfied claim_unsupported=0.93 verifier_contradicted=0.88 provider=typesafe`. The recorded outcome comes from the following `failure_recorded`, `candidate_recorded` or `question_recorded` record for that attempt. Exit 0 even when some attempts are skipped; exit 2 when the judge is unavailable before the first question. Read-only: open the journal and logs for reading only, never through `journal.Store` append paths.
