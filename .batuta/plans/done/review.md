# Plan — batuta review: cohort-based delivery review through the adapters, with a mechanical verdict
<!-- inputs: profile.md@sha256:e18a00765937 routing.md@sha256:8ddd757ea7e2 -->

**Goal:** A delivery-level review that runs the same on every host: `batuta review --base <ref> [--spec <plan>]` splits the diff into cohorts, runs one read-only reviewer session per cohort through the routing table's executors (the adapters' `readonly` lines, the mechanism the verifier gate already uses), merges the findings mechanically, checks the plan's criteria as a spec, and derives a `SHIP / FIX_BEFORE_SHIP / REWORK` verdict by rule. Distilled from pedronauck/skills `deep-review` (cohorts, evidence discipline, taxonomy, linter overlap, mechanical verdict); none of its scripts, state or publishing. Refs the July decision in batuta-ai/batuta `docs/specs-history/2026-07-26-destilacao-pedronauck-skills-design.md`.

## Decisions and context

Why in core: every Batuta skill must run on every supported CLI host (Claude Code, Codex, Cursor, opencode, Antigravity, Compozy); a host's fan-out tool is not available on the others, so parallel reviewer sessions run through core's executor runner exactly like `batuta loop` and the verifier gate do. The skill `batuta-review --deep` (batuta-ai/skills, out of this plan) will call this subcommand and translate the verdict.

Reuse: `executor.Adapter.ReadonlyCommand` and `executor.Subprocess.Execute` (see the verifier gate in `loop/attempt.go` around line 400 and `gates/gates.go`), the routing table loader (`routing.ParseRoutingTable`, `RoutingTable.Generation`), the profile loader (`loop/profile.go`), the `<<<REPORT`/`<<<FINDINGS` marker convention from `skills/batuta/references/verification.md`. The new `review` package depends on `executor`, `routing`, `inventory` and `gates`; `cmd/batuta` adds `review` following the three-edit rule (case in `run`, handler, name in `commands` and `usage`). Standard library only for the package (no new module).

Taxonomy (severity): blocker = wrong behaviour on a plan criterion, data loss, security, build or test break; major = wrong behaviour off-criterion, missing test for a changed invariant, resource leak, race; minor = clarity, dead code, duplication, docs drift; nit = style. Kinds: defect (Premise → Path → Verdict) and advisory (Premise → Improvement → Fix). Verdict is derived, never felt: any accepted blocker or violated criterion → REWORK; any major → FIX_BEFORE_SHIP; else SHIP.

Every Go command in the sandbox is prefixed with `HOME=/private/tmp/batuta-home GOCACHE=/private/tmp/batuta-gocache GOPATH=/Volumes/Home/francisross/go GOMODCACHE=/Volumes/Home/francisross/go/pkg/mod GOFLAGS=-mod=mod GOPROXY=off` (`GOTOOLCHAIN` stays `auto`). Do not edit `go.mod` or `go.sum`, do not run `go mod tidy`. Environment setup is never a question. Tests use fake adapters and scripted subprocess results as `loop/loop_test.go` does; no network, no real executor.

**Task 1.** Generated and vendored detection: paths matching `vendor/`, `node_modules/`, `*.lock`, `go.sum`, `*.pb.go`, `*_generated.go`, `*.min.*`, `dist/`, `build/`, and a first line containing `Code generated` or `DO NOT EDIT`. Hunks come from `git diff -U0 <base> -- <file>` parsed into `{start, count}` ranges for new lines. Cohort assignment is deterministic (sorted paths, greedy fill) so a repeated run yields the same manifest.

**Task 2.** The optional `review` role row of `.batuta/routing.md` (second table, like `research`) is parsed in `routing/table.go` (in scope, with its test): add it through the existing parser and expose it on `RoutingTable` so `RunCohorts` can read it; `batuta-route`/`batuta-init` docs live in the skills repo and are not part of this plan. The prompt is a template in `review/prompt.go` (not a skills reference): read-only instruction, the cohort's hunks with file paths and new-line numbers, the rubric, the taxonomy, the output contract (`<<<FINDINGS` then one JSON object per line then `FINDINGS>>>`, followed by a free-text note), and the rule that every line reported must be a line in the hunks. Sessions run in temporary worktrees at the head under review or in the checkout with a tree signature check before and after (the gate 1 signature helper), never with write access.

**Task 3.** Spec criteria are the `Accept` entries of every task in the plan file (`routing.LoadPlan` / `gates.ParseCriteria`); the sweep session receives them as a numbered list with the diff summary and must answer each with `satisfied|violated|not-applicable` and a path. `Lint:` is a new optional line of `.batuta/profile.md` (document it in `loop/profile.go`); its output is parsed as `path:line[:col]: message` (Go vet, golangci-lint, eslint --format unix, ruff all print that shape).

**Task 4.** `<slug>` in the artefact directory is the spec's slug when given, else the branch name sanitised. `review.md` is the printed report verbatim so it can be attached to a PR by hand. Exit codes are the contract for skills and CI.
