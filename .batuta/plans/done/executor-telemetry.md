# Plan — executor telemetry: output tail of unclean sessions, CLI-reported usage

**Goal:** Record in the journal what later decisions need and the batuta does not keep today. First, the bounded, redacted output tail of every executor session that does not end cleanly, which is the data a provider-limit classifier would be tested on. Second, the token usage a CLI reports at the end of a session, declared per adapter, so lane and cost comparisons stop reading "unknown" for every worker.

## Decisions and context

Go standard library only, frozen exported signatures except the additions named in the tasks, conventional commits. Nothing here changes routing, gates or outcomes; it only adds fields to `executor_finished`. The journal is local and excluded from git, but it is read by replay and benchmark tooling, so the tail must be bounded and redacted before it is written.

**Task 1.** The record is written in `loop/attempt.go` at the `r.locked(KindFinished, …)` call. Add `output_tail` only in the unclean case: an object `{"stdout": "...", "stderr": "..."}` built with `executor.Tail(result.Stdout, 40)` and `executor.Tail(result.Stderr, 40)`, each cut to its last 4096 bytes on a UTF-8 boundary, then passed through `redactText(value, r.root)` and `dropSecretLines` (both in `loop/judgment.go`, read them, do not edit that file). The rate-limit wait loop in the same function records `KindLimitWait` before re-running the same attempt; add the same `output_tail` there from the rate-limited `result`, since today only the final invocation reaches `executor_finished` and every limit message before it is lost. Put the new tests in the new file `loop/finished_telemetry_test.go`, driving a fake executor the way the existing loop tests do.

**Task 2.** `executor.Usage` already exists for ACP (`executor/usage.go`); add one field `ReportedTotalTokens` (`*int64`, JSON name `reported_total_tokens`, omitempty) for CLIs that print only a total, and leave `TotalTokens()` unchanged. `Result` gains `Usage *Usage`. The adapter field is read in `ParseAdapter` like `limit_regex`. The regex is matched against the same tail string `Outcome` builds for `limit_regex`; use `(?s)` only if the adapter writes it. For the total-only example, a pattern such as `tokens used\s+(?P<total>[0-9][0-9., ]*)` must yield 292834. The skills adapters are a separate repository and are not changed by this plan.
