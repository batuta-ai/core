**Task 1.** Findings to close, verbatim from the review:
- [1] blocker · loop/loop_test.go:1902 · premise: The concurrent-resume test requires the losing call to return 'owned by pid'. acquirePresence creates the lock with O_EXCL before writing its JSON; acquireDeliveryOwnership immediately inspects an existing lock. · path: After the winner creates the file but before it writes the payload, the loser can read an empty file and return 'loop: inspect presence lock: parse presence lock: unexpected end of JSON input'. Exactly one Resume still succeeds, but this assertion fails. · verdict: The new test can fail depending on goroutine scheduling despite successful ownership exclusion. · fix: Assert one successful owner and one error in this contention test; retain the exact ownership-message assertion in the existing initialized-lock tests. Add a controlled interleaving test separately if initialization-race behavior must be specified.
- [2] blocker · loop/presence.go:139 · premise: Every heartbeat truncates the ownership file before writing its replacement JSON; inspectPresence rejects empty or incomplete JSON. · path: If the process exits between Truncate and Write, the lock remains malformed. Subsequent acquireDeliveryOwnership calls return the inspection error before checking staleness, even after presenceFresh has elapsed. Resume, Answer and Abandon all use this acquisition path. · verdict: A crashed heartbeat can permanently prevent delivery recovery without manually removing the lock. Concurrent readers can also receive transient parse errors during healthy refreshes. · fix: Use a crash-safe heartbeat representation coordinated with exclusive ownership, and provide guarded recovery for stale malformed locks. Test interruption after truncation and inspection during refresh.
- [3] blocker · loop/presence.go:242 · premise: The inode/owner check and os.Remove are separate operations with no cross-process exclusion. · path: Two resumes inspect the same stale lock and both pass this check. One removes it and acquires a replacement; the other then removes that replacement and acquires its own lock. Both can proceed to journal writes. Store.Append independently reads the previous sequence and digest, so overlapping appends can break the hash chain. · verdict: Concurrent stale takeovers can leave two running owners and corrupt the delivery journal. · fix: Serialize acquisition, stale takeover and removal with a cross-process guard; recheck identity and freshness under that guard. Add a deterministic test interleaving two stale takeovers.
- [8] major · loop/runner.go:261 · premise: Resume now acquires ownership and starts its heartbeat, but releases ownership only when Resume fails or Run returns. · path: cmd/batuta/main.go calls Resume before checking --dry-run. That path calls DryRun and returns without Run; DryRun does not release ownership, and callers have no exported release method. · verdict: A successful resume preview leaves the lock behind, preventing an immediate real resume until it becomes stale. In a long-lived caller, the heartbeat and file descriptor remain active and can block resumption indefinitely. · fix: Provide an explicit ownership cleanup method and defer it in callers immediately after Resume succeeds, including the dry-run path, or implement preview loading without acquiring persistent ownership.

The lock file is `.batuta/journal/<delivery>.lock` (`loop/presence.go`); the guard is `.batuta/journal/<delivery>.lock.guard`, opened and locked for the duration of acquire, takeover and remove (`syscall.Flock` on unix in `loop/flock_unix.go`, `LockFileEx` through `syscall` in `loop/flock_windows.go`, build tags; `routing/flock_unix.go` is the existing pattern to copy, not to import). Heartbeat: write `<lock>.tmp` then `os.Rename` over the lock; readers keep `inspectPresence` but a parse error on a lock whose mtime is older than the freshness window counts as stale under the guard. `Release()` is idempotent and also runs at the end of `Run`; `RunRoadmap` in `loop/roadmap.go` (in scope) releases on its early returns too. A previous attempt's work is parked under `refs/batuta/parked/hardening-review-fixes-2/task-1-e1` (`git show <ref> --stat`); reuse what holds.
