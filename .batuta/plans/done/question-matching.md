## Decisions and context

Go standard library only, conventional commits, table-driven tests with `t.Parallel()`. Read `.batuta/judge-research.md` section 15 first: its word lists, order, options, wording, threshold and counts are frozen and must be copied, not reinterpreted; where this plan and section 15 differ, section 15 wins and the difference is a question for the conductor. Nothing in `loop/`, `judge/`, `classify/`, `gates/` or `routing/` changes; no code answers a question. Every CLI form prints compact JSON or TSV; exit 0 pass, 1 error, 2 unavailable judge.

Environment setup is never a question. For Go inside a sandbox on this machine: `HOME=/private/tmp/batuta-home GOCACHE=/private/tmp/batuta-gocache GOPATH=/Volumes/Home/francisross/go GOMODCACHE=/Volumes/Home/francisross/go/pkg/mod`, `GOTOOLCHAIN` stays `auto`. Run the tests named in your task's Accept lines. If the sandbox blocks the Go build cache or a loopback listener, write the tests and say so in the report: the conductor's gate runs the whole suite.

**Task 1.** A plan is `routing.Plan` and a task `routing.PlanTask` (`routing/plan.go` ~45–70); `plan.ContextFor(task.Number)` (~209) returns the task's own labelled paragraph together with the unlabelled ones, which is the order section 15 wants after the title, Scope and Accept. Bounding and the secret filter exist unexported in `classify/classify.go` ~152–190 (`boundContext` and its line test): copy both into `questions/passage.go` with a comment naming the origin, since `classify/` must not change. `judge.Question`, `judge.QuestionChoice` and `judge.Answer` are in `judge/judge.go` ~36–73; `Criteria` is the map from option to its description. The eleven extensions are `.go .ts .tsx .js .php .md .json .yaml .yml .lock .sh`; "under a Scope entry" means the entry is a directory prefix of the token or a glob that matches it with `path.Match`.

**Task 2.** `questions` is a new form of `batuta judge`, dispatched in `runJudge` (`cmd/batuta/judge.go` ~29–45) beside `corpus` and `objections` is not there, so add only `questions` to both lists of available forms. Journals are read the way the bench reads them (`readBenchJournals`, `cmd/batuta/judge_classify.go` ~306); a `question_recorded` record holds `task_id` and a `detail` with `execution`, `question`, `request_id`, `run_id`, `ask_path`; an `answer_recorded` record holds `task_id` and a `detail` with `answer`, `execution`, `question`; the delivery's slug and `plan_path` are in the `delivery_opened` record's `detail`; `repo` is the base name of the workspace directory. The strict reader shape to copy is `readCalibrateRecords` and `validateCalibrateRecordFields` in `cmd/batuta/judge_classify_calibrate.go`: presence, type and allowed value of every field the code reads, the summary object last and only once. Fixture journals go under `cmd/batuta/testdata/questions/`, built from the record shapes above, never copied from a real journal; fixture plans beside them.

**Task 3.** The judge is built the way `classifyJudge` builds it (`cmd/batuta/judge_classify.go` ~118), with the decision name `question_match` for the threshold lookup; the answer-mismatch handling to copy is `benchV3RecordFor` in `cmd/batuta/judge_classify_v3.go` ~135–200, including copying `response.Usage.InputTokens` before any error return. The bench tests use a local HTTP test server. Precision of a kind is the share of questions with that `code_kind` whose `kind` label is the same; recall is the share of questions with that `kind` label whose `code_kind` is the same.

After the plan, by the conductor and not by an executor: build the corpus over the five journal directories with the binary built from the branch's last reviewed commit; write the sheet; propose the two labels per question with a note; the maintainer reviews every row; commit `labels.tsv` before the bench; run the bench once through the maintainer's login shell with `.batuta/judge-questions/judge-questions.json` (`provider: typesafe`, `model: jev-1.13.0`, `timeout_ms: 20000`); record the result in `.batuta/judge-benchmark.md` as "Question-to-plan matching, run 1". Expected, said before the labels: criterion 1 passes for `environment` and `scope_change` and is close for `continue`; the `other` residue has about 20 questions and fewer than 6 labelled `yes`, so criterion 2 is reported only.
