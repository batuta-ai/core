# Plan — batuta council: a plan judged by a council of executors before approval
<!-- inputs: profile.md@sha256:e18a00765937 routing.md@sha256:bdb31fda5c7d -->

**Goal:** `batuta council --plan <file>` asks several routed executors, through their read-only adapter lines, to judge a plan before the maintainer approves it: each counsellor critiques the plan alone, then reviews the other critiques anonymously and ranks them, and a chairman from the routing table writes the synthesis. The command never approves a plan; it writes artefacts and an exit code the `batuta-council` skill reads.
**Created:** 2026-10-08 · **Status:** approved

## Decisions and context

Go standard library only, conventional commits, table-driven tests with `t.Parallel()`, temp dirs through `tempDir(t)`. `cmd/batuta` must build on linux, darwin and windows. Every CLI form prints compact JSON or TSV except the human report the subcommand documents. Release tooling (`CHANGELOG.md`, `.release-please-manifest.json`, `release-please-config.json`, `.goreleaser.yaml`, `.github/workflows/*`) is never touched.

Environment setup is never a question. `GOCACHE` is set to a writable directory and the Go 1.26.4 toolchain is first on PATH with `GOTOOLCHAIN=local`: run `go test` plainly. If your shell still has `GOROOT` pointing to the mise Go 1.24.2 install, run `env -u GOROOT go test …`; if that is refused too, finish the code and tests, say so in your report and stop — the conductor's gate runs the suite. Tests use fake adapters and fake subprocess runners; no test calls a real model.

Design source, decided with the maintainer on 2026-10-08: Andrej Karpathy's `llm-council` (https://github.com/karpathy/llm-council, commit `92e1fcc`, no licence declared). Only the design is adopted: independent first opinions, anonymized peer review with a `FINAL RANKING:` list and an averaged rank, and a chairman synthesis. No text, prompts or code are copied. Batuta's use is narrower: the question is always "is this plan ready to approve", the counsellors are routed executors run headless through their read-only lines, and the output is evidence for the maintainer, never an approval. The mechanics live in core so every host gets the same council, as with `batuta review`; the `batuta-council` skill in `batuta-ai/skills` is planned after this plan and only calls the command, reads `council.md` and helps the maintainer decide.

Decided with the maintainer: the chairman is a routing row (`| chairman | high | codex | gpt-6-sol |` style in the role table), defaulting to the high lane row.

**Task 1.** The role table is parsed by `parseRoutingRoles` (`routing/table.go` ~189): rows with a `Role` column, roles `review` (one) and `research` (many), CLI executors and exact models only. `RoutingTable` (~48) carries `Review` and `Research`. Add `Council []RoutingRow` (or roles) and `Chairman *RoutingRole` the same way; the defaults are computed from `Rows` when the role rows are absent.

**Tasks 2–3.** The read-only invocation is `executor.Adapter.ReadonlyCommand(executor.Request{Prompt, Cwd, Model, Effort})` (`executor/adapter.go` ~317), run through `executor.Subprocess.Execute`; `review/session.go` `RunCohorts` (~132) shows the pattern to follow for parallel read-only sessions, the tree-signature check before and after, timeouts and failure recording, and `review/report.go` `reviewOutputTail` the tail redaction (use `executor.DropSecretBearingLines`). A finding id is the critique label plus the finding's index (`A1`, `A2`, `B1`…). Severity is `blocker`, `major` or `minor`. Merging findings across critiques is by task number and a normalized claim; when unsure, keep them separate — the chairman reconciles.

**Task 4.** Subcommands are wired in `cmd/batuta/main.go` (`run` switch ~188, `var commands` ~230, usage text at the top). `batuta review` (`runReview` ~1015) shows artefact directories, `--out`, guarded writes and exit mapping. Exit 2 means "the council recommends revising", not a failure of the command.
