# Plan — standing grants on answers
<!-- inputs: profile.md@sha256:e18a00765937 routing.md@sha256:bdb31fda5c7d -->

**Goal:** An answer to a parked task can carry a structured grant: paths and operations, valid until the task ends. The grant persists on the delivery graph. Every later brief of that task renders it as a standing authorization, and the granted paths join the task's effective Scope, never past the brief's Boundaries. When the executor asks again without naming something outside the grant, the runner answers from the grant inside the same execution instead of parking, within a bounded number of turns and the execution's own time budget. That closes Tempo finding 4.5, core part.

## Decisions and context
Source: Tempo finding 4.5 (`.batuta/feedback/2026-09-21-tempo-mvp-triage.md`, row 4.5; retrospective `.batuta/feedback/2026-09-21-tempo-mvp-retro.pt-BR.md`, lines 84–87). Its acceptance criteria are: a grant bound to a task is not asked for again without a real expansion of scope; a new question states exactly what differs from the grant; a restart never silently turns a limited grant into a broad one. How the conductor writes grants (batuta-ai/skills) is a separate plan. The watch TUI answer overlay stays text-only in this plan.

Maintainer decisions, 2026-10-24: (a) a question is covered unless it ends with a `Beyond grant:` clause naming at least one ungranted item, which is a deterministic rule with no judge; an empty or malformed clause parks; (b) a grant reply does not consume an execution, so it re-dispatches inside the current attempt and `MaxTaskExecutions` and every graph invariant built on it stay unchanged. A cap of 3 grant turns per execution, the repeat rule and one deadline per execution, shared by all its turns, bound the turns. Grant turns do not reserve tokens: the attempt's `TokenAllowance` (`routing/graph.go:571-627`) is a reservation on the graph, not a limit the executor receives, and turns leave it unchanged; (c) a grant is valid until the task ends in this delivery, never in another task or delivery; (d) the grant enters through flags on `--answer`, placed before the answer text because `flag.FlagSet` stops at the first positional argument, and through a new `AnswerQuestionGrant`, while `AnswerQuestion` keeps its signature because the console calls it.

A grant only adds. The standing grant is the union of the explicit grants recorded on the task's answered attempts, normalized. Nothing widens it by default, and resume and replay read it from the graph, so a restart cannot broaden it. An answer without grant flags behaves exactly as today.

Boundaries. Today the `## Boundaries` rules exist only as brief prose (`loop/brief.go:112`). `gates.Scope` (`gates/gates.go:251`) checks only the Scope it receives. A grant must never extend past them. The single list lives in `routing/grant.go` as `routing.GrantBoundaryPaths`, with the predicate `routing.IsGrantBoundary(path string) bool`; no other task redefines it. The entries are: `WORK.md` and `.batuta/**` at the root; CI configuration at the root (`.github/**`, `.gitlab-ci.yml`, `.circleci/**`, `azure-pipelines.yml`, `.buildkite/**`, `Jenkinsfile`); licenses at any depth (`LICENSE*`, `COPYING*`, `NOTICE*`); and lockfiles at any depth (`go.sum`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lockb`, `bun.lock`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `Gemfile.lock`, `composer.lock`). A changed path passes the scope gate when the plan Scope covers it, exactly as today, including any boundary file the plan Scope itself names through an allowed dependency. A changed path also passes when the grant covers it and it is not a boundary path. Nothing else passes.

Accepted trust limit: the executor reports its own coverage. A question with no `Beyond grant:` clause gets the grant reply even when it concerns a design choice, and the reply says to use the clause for scope questions. Task 11 states this limit.

Proofs. Every named proof has the form `out=$(go test -run '^Name$' -v ./pkg/) && printf '%s' "$out" | grep -q -- '--- PASS: Name '`. It requires `go test` to exit 0 and the exact test name, followed by a space, to pass, because `go test -run` exits 0 when no test matches and a subtest's `--- PASS: Name/sub` must not count. Package gates use `go test -timeout 15m ./loop/` because the loop suite runs for minutes. `TestLoopStopsWorktreeProcesses` is a known flake (one input/output failure that passed on rerun); a rerun is the response, never a skip.
