# Plan — Dashboard v2: panels, waves as phases, gates, live logs, keyboard
<!-- inputs: profile.md@sha256:e18a00765937 routing.md@sha256:8ddd757ea7e2 -->

**Goal:** Replace the TSV panel of `batuta loop --dashboard --watch` with a terminal dashboard in the style of the maintainer's reference: a header, four boxed panels (execution, engine, progress with bars, current work), a task table grouped by wave with status, attempt and gates G0–G3, a live tail of the active executor's log, and keyboard navigation. Standard library only, ANSI 16 colours with an ASCII fallback, labels in English or Portuguese from the locale, golden-tested against the approved mocks; `batuta watch` opens it with watch by default. Closes core #64.
**Created:** 2026-09-06 · **Status:** approved

## Decisions and context

Visual reference: the maintainer's "LOOP ENGINEER" terminal, revised on 2026-09-06 through a design canvas and a critique (score 19/36 before the revision). The approved mocks are the goldens: `docs/dashboard-mock/mock-<state>-<width>.txt` (states calm, question, limit, blocked, conflict; widths 120, 80, 60) plus `mock-calm-120-pt-unicode.txt` and `mock-calm-120-en-ascii.txt`; they were generated by `docs/dashboard-mock/gen-mock.py`, which is the layout specification (column widths, box drawing, truncation with `…`, bar geometry). Rows: header (`batuta watch · <delivery> · <project> · phase N` left, `<branch> @ <head> · <state glyph+word> · <elapsed>` right), the attention line (`needs you: no` when nothing needs a human, otherwise `? task_2 waiting answer · "<question>" · r answers`, `~ codex usage limit · resumes 23:40 (41 min) · wait 1/20`, `✗ task_2 blocked · G2 tests failed 3/3 · escalated a → b · o opens the log`, `< task_2 conflict … re-executing on <sha> · e2/4`), Context and Progress boxes, the Detail box for the selected task (title, criterion, question or reason, last record with age, worktree, log path), the table grouped by wave (wave rows are aggregates `✓ 1/1`, `> 0/1`, `· 0/2`, `✗ 0/1`; task rows carry state glyph and word, attempt `eN/4`, one Gates column with four glyphs `✓ ✗ ·`, commit), the key line, the log box. Glyphs: `✓ ✗ > · ? ~ < ^` in Unicode, `+ x > . ? ~ < ^` in ASCII; box drawing `┌─┐│└┘` or `+-|`. Labels come from a table keyed by language: English by default, Portuguese when `BATUTA_LANG`, `LC_ALL` or `LANG` starts with `pt`; values (executor names, states in the journal, task titles, log lines) are never translated. Waves are the phase rows; retries, escalations and conflict re-executions stay in the task's Attempt column.

Standard library only: no bubbletea, no x/term. Terminal size and raw mode come from platform files with build tags (`_unix.go` using `syscall` ioctl and termios, `_windows.go` using the console API through `syscall`); `cmd/batuta` must keep building on linux, darwin and windows. Colours are ANSI 16 (blue active, green ok, red error) so the terminal theme keeps the contrast; `NO_COLOR` honoured, colour off when the writer is not a TTY, ASCII glyphs and borders when the locale is not UTF-8. Golden tests fix width, language, glyphs and colour so output is byte-comparable.

Sandbox note for every Go command you run: prefix it with `HOME=/private/tmp/batuta-home GOCACHE=/private/tmp/batuta-gocache GOPATH=/Volumes/Home/francisross/go GOMODCACHE=/Volumes/Home/francisross/go/pkg/mod` (the module wants Go 1.26; the go1.26.4 toolchain is already cached under that GOMODCACHE, so `GOTOOLCHAIN` stays `auto` and nothing is downloaded; the `go` on PATH is 1.24.2 and only bootstraps). Environment setup is never a question: apply this recipe and continue; say in the report that you used it. The loop test fixture lives in `loop/loop_test.go` (`fakeExecutor`, `setup`, `fixture.options`).

**Task 1.** `executor.Subprocess.Execute` already tees stdout and stderr through `progressObserver`s; the run log is written afterwards by `writeLog` in `loop/attempt.go`. Streaming means the loop opens the log file before `Execute` and passes writers that append lines as they arrive; the final `writeLog` may rewrite the file with the header so the format stays the one documented in `docs/loop.md`.

**Task 2.** The journal is the only source: `KindOpened` (slug, branch, head, and after the roadmap plan: roadmap, phase), attempt records with the gate report, `task_progress` records (criterion START/DONE), `KindSettled` (wave, final_head, conflict_task), `limit_wait`, terminal records. Health signals: journal age, tree dirty (from the last gate 1 signature when present), last error text. Roadmap and phase fields are optional; the model shows them only when present.

**Task 3.** Port `docs/dashboard-mock/gen-mock.py` faithfully: the same column arithmetic per width (120: ID 7, title = width − 7 − 17 − 7 − 6 − 8 − 14, Status 17, Attempt 7, Gates 6, Commit 8; 80: ID 7, Status 15, Try 5, Gates 6; 60: ID 7, Status 13, Gates 6), the same box helper (title in the top border, one space of inner padding), the same bar (24 cells), the same header split, the same attention-line trimming (drop ` · ` pieces from the end until it fits). The goldens are those files copied verbatim into `loop/testdata/`; a golden mismatch is a renderer bug, never a reason to edit the golden. The view model from task 2 is extended additively when a golden shows a value it cannot carry: log lines for the log box, criterion index, total and title for Detail and Progress, the pending-wave dependency list. New fields only; the existing panel_model tests keep passing; the model stays journal-only (task 4 fills the log lines from the run log file, the renderer never reads files). Every value in a golden comes from a model field: never invent data.

**Task 6.** `watch` is a thin alias in `run`'s dispatcher: it parses `--interval`, `--once`, `--lang en|pt`, `--ascii` and an optional delivery, then calls `loop.Watch` (or `loop.Dashboard` with `--once`); the three-edit rule for a new subcommand applies (case in `run`, handler, name in `commands` and `usage`).

**Task 5.** Raw mode only for the duration of the watch; every exit path restores the terminal (deferred, and on `ctx.Done()`). Key reading runs in its own goroutine feeding a channel; the redraw loop selects on the ticker, the keys and the context. Windows: `SetConsoleMode` through `syscall.NewLazyDLL("kernel32.dll")` is acceptable inside the `_windows.go` file.
