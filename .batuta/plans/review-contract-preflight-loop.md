## Decisions and context

Go standard library only, conventional commits, table-driven tests with `t.Parallel()`, temp dirs through `tempDir(t)`. `cmd/batuta` must build on linux, darwin and windows. Every CLI form prints compact JSON or TSV. Source of the requirements: `.batuta/feedback/2026-09-21-tempo-mvp-triage.md` rows 4.6 and 4.1. Release tooling (`CHANGELOG.md`, `.release-please-manifest.json`, `release-please-config.json`, `.goreleaser.yaml`, `.github/workflows/*`) is never touched.

Environment setup is never a question. For Go inside a sandbox on this machine: `HOME=/private/tmp/batuta-home GOCACHE=/private/tmp/batuta-gocache GOPATH=/Volumes/Home/francisross/go GOMODCACHE=/Volumes/Home/francisross/go/pkg/mod`, `GOTOOLCHAIN` stays `auto`. Run the tests named in your task's Accept lines. If the sandbox blocks the Go build cache or a loopback listener, write the tests and say so in the report: the conductor's gate runs the whole suite.

Decided with the maintainer on 2026-10-05: the loop probes once per route per delivery (not every attempt); `batuta dispatch` probes only with `--preflight`. A route is executor, model, effort and transport together.

Decided while planning, open to change at approval: `findings.json` stays a JSON list of findings so existing readers keep working, and the review failures go to a fifth artifact `review_failures.json` instead of into `findings.json`. The last line of `review.md` stays exactly `Verdict: <verdict>` because the loop's supervision parses it with `^Verdict: (SHIP|FIX_BEFORE_SHIP|REWORK)\n?\z` (`loop/supervision_review.go` ~447); the reason goes into a `Review failures:` section above it, not into the verdict line the triage sketched.

**Task 1.** Dispatch lives in `executor/dispatch.go` (`Dispatch`, exit classes 0 completed, 1 failed, 2 unavailable or invalid_arguments, 3 waiting_input, 4 rate_limited, 5 uncertain; 124 and 130 for timeout and interrupt); 6 is free. The loop's attempt is `runAttempt` (`loop/attempt.go` ~175); failures go through `recordFailureWithPolicy` (~883), whose conducting policy retries once on the same runtime and then escalates one row, writing the trail verdict `⏫ escalated from …` (~944). Journal records go through `Runner.record` (`loop/runner.go` ~942). The probe exists because a headless executor that can edit files but cannot run commands parked whole deliveries in `waiting_input` on the Tempo run; the probe brief stays one paragraph and never mentions the task.

**Task 1.** Why the Scope is wider than in the first plan: the first delivery (`review-contract-preflight-20261005-181638`, abandoned after tasks 1–5 integrated) failed its first attempt because the fake executors in the `cmd/batuta` loop tests never print `BATUTA-CAPABLE`, so the probe failed every route there (`executor_incapable … no_marker`). The test files added to Scope (`cmd/batuta/main_test.go`, `cmd/batuta/main_unix_test.go`, `loop/attempt_test.go`, `loop/answer_question_test.go`) may change only so that their fake executors answer the probe, or so that their expected command calls count the probe; nothing else in them changes. No production flag or branch may exist only to skip the probe in tests.

**Task 1.** A previous attempt's work is kept in git and may be reused after reading it, never applied blindly: `git show refs/batuta/salvage/review-contract-preflight/task-6-e2` (second attempt at question time: `loop/capability.go`, `loop/capability_test.go` and edits to `loop/attempt.go`, `loop/runner.go`, `loop/loop_test.go`, `docs/loop.md`; the probe follows the same CLI preflight path as dispatch and keeps the task backend separate from the route probe's backend) and `refs/batuta/parked/review-contract-preflight/task-6-e1` (first attempt).
